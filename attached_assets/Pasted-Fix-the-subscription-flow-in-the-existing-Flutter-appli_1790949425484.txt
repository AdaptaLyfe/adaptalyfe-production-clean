Fix the subscription flow in the existing Flutter application.

## Goal

The existing **Web React + React Native + Wrapper** application already has a working subscription flow.

The Flutter application must follow the **same subscription business flow, screens, states, user experience, entitlement logic, and backend behavior** as the existing Web/React Native + Wrapper implementation.

Flutter should use:

* **Android → Google Play Billing subscriptions**
* **iOS → Apple App Store subscriptions**

Do NOT create a completely different subscription system for Flutter.

---

# 1. First Inspect Existing Implementations

Before changing Flutter code, carefully inspect the existing:

### Web React application

Find and understand:

* Subscription/Pricing screen
* Subscription plans
* Trial logic
* Monthly/yearly plans if available
* Subscribe button behavior
* Existing API calls
* Payment status handling
* Subscription success/failure states
* Active subscription detection
* Cancellation/expiration handling
* Restore subscription behavior
* User entitlement/access logic
* Backend subscription verification
* Webhook/subscription status updates

### React Native + Wrapper application

Find and understand:

* Subscription UI
* Plan selection
* Purchase flow
* Android billing implementation
* iOS purchase implementation
* Restore purchases
* Existing backend/API integration
* Loading states
* Success/error handling
* Existing subscription status checking
* How the app decides whether a user has premium/subscription access

Treat the existing Web and React Native + Wrapper implementation as the **source of truth for business logic and user flow**.

Do not assume the Flutter implementation should work differently.

---

# 2. Flutter Platform Billing

Implement native platform subscriptions correctly.

## Android

Use **Google Play Billing** through the Flutter project.

The Android purchase flow must be:

Flutter Subscription Screen
→ Select Plan
→ Google Play subscription purchase sheet
→ Google Play processes payment
→ Flutter receives purchase result
→ Verify purchase
→ Send required purchase information to backend
→ Backend verifies subscription
→ Update user's subscription/entitlement
→ Flutter refreshes subscription state
→ Show the same success/access state as React Native + Wrapper

Do NOT treat a successful local purchase callback alone as permanent subscription access.

The backend should remain the source of truth for entitlement where the existing application already uses backend verification.

---

# 3. iOS

Use **Apple App Store In-App Purchases / StoreKit** through the Flutter project.

Flow:

Flutter Subscription Screen
→ Select Plan
→ Apple purchase sheet
→ Apple processes payment
→ Flutter receives transaction
→ Verify transaction/receipt according to the existing backend architecture
→ Send required purchase information to backend
→ Backend verifies subscription
→ Update user's subscription/entitlement
→ Flutter refreshes subscription state
→ Show the same success/access state as React Native + Wrapper

Support Apple's restore purchases flow.

# 6. Subscription State

Create/use a single reliable subscription state.

The Flutter app should correctly handle:

* Not subscribed
* Loading
* Purchase pending
* Purchase successful
* Active subscription
* Purchase failed
* Purchase cancelled
* Purchase restored
* Subscription expired
* Subscription cancelled but still active
* Billing problem
* Verification failed
* Network/API failure

Do not show "Active Subscription" only because the purchase button returned successfully.

After purchase, refresh the actual subscription status.

# 7. Restore Purchases

Implement a visible **Restore Purchases** action where it exists in the current Web/React Native + Wrapper flow.

For iOS:

* Use Apple's restore mechanism.
* Re-check the user's entitlement after restoration.

For Android:

* Query existing purchases/subscriptions.
* Re-check the backend subscription status.

Restoration must not create a duplicate subscription.

# 9. BLoC Architecture

Use the existing Flutter architecture and BLoC pattern if BLoC is already being used.

Prefer a structure similar to:

```text
SubscriptionScreen
        ↓
SubscriptionBloc
        ↓
SubscriptionRepository
        ↓
Platform Billing Service
        ↓
Google Play / Apple App Store
        ↓
Backend Verification API
        ↓
SubscriptionRepository
        ↓
SubscriptionBloc
        ↓
SubscriptionScreen
```

Do not put billing, API, and verification logic directly inside widgets.

Keep the implementation easy to maintain.

---

# 10. Purchase Listener

Make sure the Flutter billing implementation correctly listens for purchase/transaction updates.

Handle all purchase states.

For each purchase:

```text
pending
purchased
restored
error
cancelled
```

Do not leave purchase streams/listeners active after the relevant lifecycle ends.

Avoid:

* Duplicate purchase listeners
* Multiple API calls for the same transaction
* Multiple BLoC subscriptions
* Memory leaks
* Calling `setState` after dispose
* Processing the same transaction repeatedly

---

# 11. Complete Purchase Lifecycle

Implement this lifecycle:

```text
User opens Subscription
        ↓
Load subscription products
        ↓
Display available plans
        ↓
User selects plan
        ↓
Start platform purchase
        ↓
Google Play / Apple Store purchase UI
        ↓
Purchase result
        ↓
Validate purchase
        ↓
Send purchase to backend
        ↓
Backend verifies purchase
        ↓
Subscription status updated
        ↓
Refresh current user subscription
        ↓
Update Flutter state
        ↓
Show subscribed UI / unlock premium features
```

If verification fails:

```text
Purchase completed
        ↓
Verification failed
        ↓
Do NOT incorrectly show permanent premium access
        ↓
Show proper error/retry state
```
