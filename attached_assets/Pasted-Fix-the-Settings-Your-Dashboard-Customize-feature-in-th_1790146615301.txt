Fix the **Settings → Your Dashboard → Customize** feature in the existing Flutter project.

### Bug

The dashboard customization is not being applied correctly.

Current behavior:

1. User opens **Settings → Your Dashboard → Customize**.
2. User enables a previously disabled skill/module.
3. User disables a previously enabled skill/module.
4. User returns to **Your Dashboard**.
5. The dashboard does not always reflect the latest customization.
6. Some modules may still appear even after being disabled, or enabled modules may not appear.
7. The issue may reappear after navigating away and coming back.

### Required behavior

The **Your Dashboard** must always exactly match the user's latest customization settings.

Example:

* If a module is **enabled** → it must appear on Your Dashboard.
* If a module is **disabled** → it must not appear on Your Dashboard.
* If the user changes multiple modules → all changes must be reflected immediately after returning to Your Dashboard.
* The state must remain correct when navigating between Settings and Dashboard.
* The state must remain correct after leaving and reopening the relevant screens.
* Do not require the user to restart the app to see changes.

### Important: Find the root cause

Do NOT simply add `setState()` or force a screen refresh.

First inspect the existing implementation and identify:

* Where dashboard customization is stored.
* Which state management approach is currently used (BLoC/Cubit/Provider/etc.).
* How enabled/disabled modules are saved.
* How Your Dashboard reads the customization state.
* Whether Settings and Dashboard are using different state/data sources.
* Whether the dashboard is using stale cached data.
* Whether navigation keeps an old Dashboard widget/state alive.
* Whether customization changes are persisted correctly.
* Whether the dashboard list is generated from the latest customization data.

### Fix requirements

Implement a proper single source of truth for dashboard customization.

When the user changes a module:

1. Update the customization state.
2. Persist the updated value using the project's existing storage/backend architecture.
3. Notify/update the appropriate state manager.
4. When Your Dashboard becomes visible, it must read the latest customization state.
5. Rebuild only the necessary dashboard content.
6. Make sure old/stale module visibility values cannot override the latest values.

### Persistence

If customization is stored locally:
