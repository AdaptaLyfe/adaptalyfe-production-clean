### BUG 1 — Editing an Event Reloads the Whole App

Current issue:

* User opens Calendar.
* User selects an existing event and taps Edit.
* User modifies the event and saves it.
* After saving, the whole Flutter app reloads/reinitializes.
* User is redirected to the Home page instead of returning to the Calendar page/parent page where the edit was started.

Required behavior:

1. When editing an event, preserve the current navigation context.
2. After successfully saving the edited event:

   * Do NOT restart/reload the entire application.
   * Do NOT navigate to Home.
   * Return to the exact parent Calendar screen/page from where the edit was started.
3. Refresh only the required Calendar/event data.
4. Preserve the current Calendar state where possible:

   * selected date
   * selected view (day/week/month)
   * scroll position if applicable
   * filters if applicable
5. Use the existing BLoC/state-management and repository flow.
6. Do not use `runApp()`, app-level navigation reset, forced route replacement, or any workaround that recreates the entire application.
7. Check for incorrect `Navigator.pushReplacement`, `pushAndRemoveUntil`, `go()`, `context.go()`, app restart logic, or state initialization that may be causing the Home redirect.
8. Make sure the fix works for both creating and editing events.

### BUG 2 — "All Day Event" Is Not Displayed Correctly

Current issue:

* While creating/editing a Calendar event, the user can enable the **"All day event"** toggle.
* After saving, the event is not displayed correctly as an all-day event on the selected date.

Required behavior:

#### Case A — All Day Event = ON

If the user enables **"All day event"**:

* Treat the event as an all-day calendar event.
* The event must appear in the **All Day** section/header of the selected date.
* It must not appear as a normal time-based event.
* Do not require a start/end time for display.
* Store/use the correct date-only/all-day information so the event remains an all-day event after reload.
* If the event spans multiple dates, display it as an all-day event across the appropriate dates according to the selected start/end dates.

#### Case B — All Day Event = OFF

If the event is not an all-day event:

* Treat it as a normal timed event.
* Display its start and end time in the normal Calendar time area.
* Do not incorrectly place it in the All Day section.

### IMPORTANT LABELING RULE

Clarify and implement the intended behavior consistently:

* If the event is configured as a full-day event for a selected date, display it in the Calendar as **"Whole Day"** where the UI uses a full-day label.

* Do not confuse a normal timed event with an all-day event.
* Do not duplicate the event in both the All Day section and the timed section.
