Fix the Flutter bug in:

**Achievements / Rewards → Rewards**

### Bug

A user can redeem the **same reward multiple times**, even when the reward has a **"Maximum Redemptions (Optional)"** limit configured.

Example:

* Maximum Redemptions = 2
* User redeems the reward 2 times → allowed
* User tries to redeem it a 3rd time → currently still allowed ❌
* Expected → 3rd redemption must be blocked ❌➡️✅

This bug has reopened multiple times, so do NOT apply only a UI fix. Find and fix the complete redemption flow.

### IMPORTANT

First inspect the existing codebase and identify:

* Reward model/entity
* Maximum Redemptions field
* Reward details screen
* Redeem button/action
* Reward BLoC/Cubit/events/states
* Repository
* Data source/API/Firebase/database
* Redemption history/storage
* Existing redemption validation
* Existing error handling

Do not create a parallel reward system. Use the existing architecture and code.

## 1. Implement correct redemption validation

Before allowing redemption, calculate:

```text
maximumRedemptions
currentUserRedemptionCount
remainingRedemptions
```

Rules:

### If Maximum Redemptions is empty/null

Treat it as unlimited.

```text
maximumRedemptions == null
→ redemption allowed
```

### If Maximum Redemptions is set

```text
currentUserRedemptionCount < maximumRedemptions
→ allow redemption

currentUserRedemptionCount >= maximumRedemptions
→ block redemption
```

Example:

```text
Maximum = 1
Current = 0 → Allow
Current = 1 → Block

Maximum = 3
Current = 0 → Allow
Current = 1 → Allow
Current = 2 → Allow
Current = 3 → Block
```

Never use:

```text
currentCount <= maximum
```

because that incorrectly allows one extra redemption.

---

## 2. Validate using the CURRENT USER

The redemption limit must apply to the correct user.

Do not use the total number of redemptions by all users unless the existing business requirement explicitly says the limit is global.

For a user-specific redemption limit:

```text
count(redemptions where rewardId == selectedRewardId
AND userId == currentUserId)
```

Then compare that count with:

```text
reward.maximumRedemptions
```

Make sure:

* Correct reward ID is used
* Correct logged-in user ID is used
* Old/other users' redemptions are not counted
* Deleted/cancelled redemptions are handled according to the existing business rules

---

## 3. Do NOT rely only on the UI

Do NOT solve this only by disabling/hiding the Redeem button.

The actual redemption operation must validate the limit again.

Correct flow:

```text
User taps Redeem
        ↓
Check current user
        ↓
Fetch latest reward data
        ↓
Fetch latest redemption count
        ↓
Validate maximum redemption limit
        ↓
If limit reached
        ↓
Return error
        ↓
DO NOT create redemption
```

If limit is not reached:

```text
Validate
   ↓
Create redemption
   ↓
Update UI/state
```

The backend/repository/data-source validation must be the final protection.

---

## 4. Prevent race conditions / double redemption

Also check whether a user can quickly tap the Redeem button multiple times.

While redemption is processing:

```text
isRedeeming = true
```

Disable the Redeem button.

After success or failure:

```text
isRedeeming = false
```

But do not depend only on this UI protection.

If two redemption requests happen almost simultaneously, the data layer/backend must still prevent the user from exceeding the configured limit.

If Firebase/Firestore is being used, use an appropriate transaction/batch/atomic operation where possible so that:

```text
check count
+
create redemption
```

cannot incorrectly allow two requests to pass at the same time.

---

## 5. Always fetch the latest value

Do not depend on an old cached reward object.

Before redemption, make sure the validation uses the latest:

```text
maximumRedemptions
```

and latest:

```text
currentUserRedemptionCount
```

This is especially important if an admin changes the maximum redemption limit after the user opened the reward screen.

Example:

```text
User opens reward
Maximum = 5

Admin changes Maximum = 2

User presses Redeem
```

The redemption should use the latest limit of `2`, not the old cached value of `5`.

## 6. Handle unlimited rewards correctly

If:

```text

```

or the existing application represents "unlimited" using another valid value, preserve the existing application's convention.

Do NOT accidentally treat:

```text
null
```

as:

```text
0
```

because that would block all redemptions.

If `0` currently means unlimited in the existing application, preserve that behavior. Otherwise, do not change the meaning of existing data without checking the model/business logic first.
