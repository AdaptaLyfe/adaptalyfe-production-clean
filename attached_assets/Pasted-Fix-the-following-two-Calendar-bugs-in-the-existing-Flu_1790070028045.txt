## BUG 1 — Editing Calendar Event Redirects to Home

Current behavior:

1. User opens Calendar.
2. User opens an existing event.
3. User taps Edit.
4. User changes the event.
5. User taps Save.
6. The whole Flutter app reloads/rebuilds.
7. User is redirected to the Home page.

Expected behavior:

1. User opens an event from Calendar.
2. User edits the event.
3. User taps Save.
4. Save/update should happen without restarting or reloading the whole app.
5. After successful save, the user must return to the SAME parent page/context from where editing started.
6. If editing was started from the Calendar screen, return to Calendar.
7. If editing was started from another event/parent screen, return to that same screen.
8. Do not redirect to Home unless Home was actually the page from which the edit was started.

Investigate and fix:

* Navigator.push/pop behavior.
* Any `pushReplacement`, `pushAndRemoveUntil`, or navigation reset after saving.
* `MaterialApp`/router rebuilds.
* GoRouter/navigation configuration if used.
* BLoC/Cubit state changes that may rebuild the root widget.
* Authentication/session state changes.
* Calendar event update success handling.
* Any `setState`, provider, BLoC, or repository logic that incorrectly causes the application root to rebuild.
* Any code that navigates to Home after successful event update.
* Do not simply add `Navigator.pop()` without understanding the existing navigation flow.

Important:
The event update should update the existing Calendar state correctly without restarting the application or losing the current navigation stack.

## BUG 2 — "All Day Event" Is Not Displayed Correctly

Current behavior:

* While creating a Calendar event, the user can enable the "All day event" toggle.
* After saving, the event is not displayed correctly as an all-day event on the selected date.
* The event may appear as a timed event or may not appear in the expected all-day section.

Expected behavior:

### Case A — All day event = ON

If the user enables the "All day event" toggle:

* Treat the event as an all-day event.
* Store the event with the correct all-day information in the existing event model/database/API.
* The event must appear in the Calendar's ALL-DAY section for the selected date.
* Do not assign a normal time-of-day to the event.
* The selected date must remain the correct event date.
* When the event is opened again for editing, the "All day event" toggle must still be ON.
* Saving/editing the event must preserve its all-day status.

### Case B — All day event = OFF

If the user does NOT enable "All day event":

* Treat the event as a normal timed event.
* Preserve the selected start date and start time.
* Preserve the selected end date and end time if the application supports an end date/time.
* Display it in the normal timed Calendar section.
