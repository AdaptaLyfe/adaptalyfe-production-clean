Fix the Caregiver Setup caregiver invitation flow in the existing Flutter application.

### Bug

When a user invites a caregiver:

1. The caregiver receives the invitation.
2. The caregiver accepts the invitation successfully.
3. The invitation status changes to `ACCEPTED`.
4. However, the caregiver's name does NOT appear in the **"Active caregivers"** list.
5. The same caregiver still appears in the **"Invitations"** section with `ACCEPTED` status.

This bug has been fixed/reopened multiple times, so do NOT apply a temporary UI-only fix. Find and fix the actual root cause across the complete data flow.

### Required behavior

After a caregiver accepts an invitation:

* The caregiver must immediately/automatically appear in **Active caregivers**.
* The accepted invitation must NOT continue to appear in the active/pending **Invitations** list.
* If the Invitations section intentionally displays invitation history, an `ACCEPTED` record may remain there only as history, but it must not be treated as a pending invitation.
* Active caregiver data must come from the correct source of truth.
* The relationship between the inviter/care recipient and accepted caregiver must be stored correctly.
* Refreshing the page/app must still show the caregiver under Active caregivers.
* Logging out and logging back in must still show the caregiver correctly.
* The fix must work for every caregiver, not only the caregiver used during testing.

### IMPORTANT: Investigate the root cause first

Before changing code, trace the complete flow:

1. Caregiver invitation creation.
2. Invitation document/model creation.
3. Invitation ID and caregiver/user ID.
4. Invitation acceptance.
5. Backend/Firebase/Firestore update after acceptance.
6. Creation/update of the caregiver relationship.
7. Active caregivers query.
8. Invitations query.
9. Flutter repository/data-source layer.
10. BLoC events and states.
11. UI listeners/builders.
12. Refresh/reload behavior.

Check whether the problem is caused by:

* Wrong Firestore collection/document.
* Wrong user ID/caregiver ID.
* Wrong parent/care-recipient ID.
* Accepted invitation not creating the caregiver relationship.
* Field-name mismatch.
* Different enum/status values such as `accepted`, `ACCEPTED`, or `Accepted`.
* Active caregiver query filtering incorrectly.
* Invitations query incorrectly including accepted invitations as pending.
* BLoC state not being refreshed after acceptance.
* Cached/stale data.
* Stream/query not listening to the correct document.
* Duplicate models or different data sources being used for Active caregivers and Invitations.
* Race condition between accepting the invitation and loading Active caregivers.
* Missing Firestore update.
* Security rules preventing the required document from being read/written.
* Null/missing caregiver profile information.

### Data consistency requirement

There should be one clear source of truth for an accepted caregiver relationship.

When invitation acceptance succeeds, make sure the required relationship/data is persisted correctly.

Conceptually the flow should be:

Invite caregiver
→ Invitation created
→ Caregiver accepts
→ Invitation status becomes ACCEPTED
→ Caregiver relationship becomes ACTIVE
→ Active caregivers query returns caregiver
→ UI updates
→ Invitations no longer treats it as pending

Do not rely only on local Flutter state to make the caregiver appear.

### BLoC/state requirement

After successful acceptance:

* Update the backend first.
* Refresh/reload the caregiver relationship data.
* Refresh the invitation data if required.
* Emit the correct BLoC state.
* Make sure the UI rebuilds from the updated state.
* Avoid forcing the UI to manually insert a fake caregiver into the list.

If the app uses streams, verify that the stream actually listens to the correct Firestore documents/query.

### Invitations section

Check the existing logic carefully.

If the Invitations section is supposed to show only pending invitations, its query/filter must exclude:

* `ACCEPTED`
* `DECLINED`
* `EXPIRED`
* other completed statuses

Do not simply hide `ACCEPTED` from the UI if the backend/query logic is incorrect. Fix the data/query logic at the appropriate layer.

### Active caregivers section

The caregiver must remain visible after:

* Logout/login

If a migration/backfill is genuinely required, explain exactly what is needed before implementing it.
